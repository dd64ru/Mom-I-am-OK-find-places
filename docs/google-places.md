# Google Places primary resolver

The production composition is `GooglePlacesPoi → FallbackPoi → NominatimPoi`. OpenAI vision/web verification supply bounded text only. Coordinates come from deterministic providers and require explicit Telegram confirmation before a canonical Place is saved.

## Protocol and matching

Use [Places API (New) Text Search](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places/searchText): `POST https://places.googleapis.com/v1/places:searchText`. There is one request per resolution, ten results maximum, a ten-second deadline, no redirects and a 200 KB response bound. Only structured venue/native names, canonical/corrected locality, address clue and country are queried; images, visible text, Telegram captions/conversation/IDs are excluded. English is preferred; native names and cited aliases remain useful.

The field mask requests only `places.id`, `places.displayName`, `places.formattedAddress`, `places.location`, `places.types`, `places.addressComponents`, `places.attributions` and `nextPageToken`. Display name and geographic validation require Text Search Pro fields; no reviews, photos, opening hours, ratings, contact details or Place Details request is used. There is no wildcard, pagination/research loop or Google response cache.

Names must equal canonical/native/cited alias evidence after Unicode, diacritic and punctuation normalization. Abbreviations must already be supplied as aliases; there is no fuzzy ranking, prefix or edit-distance selection. Locality/country must match; an explicit city correction remains a hard constraint and workspace hints cannot select another chain branch. Address clues are checked against formatted/components with bounded street abbreviation normalization and token boundaries, so number 18 does not match 180. Specific travel types cover dining, shops, universities, landmarks and natural/visitor destinations; generic route/address/political/establishment-only results are rejected.

Exactly one reliable ID is resolved. Multiple plausible candidates or a truncated matching page remain ambiguous. A contradictory duplicate ID/coordinate response is invalid. Google's [Place location / LatLng contract](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places#LatLng) specifies WGS84 unless otherwise stated; this implementation uses those coordinates directly without China-specific offsets or undocumented conversions.

## ADC, quota and owner preparation

Authentication uses [Application Default Credentials](https://cloud.google.com/docs/authentication/application-default-credentials) through `google-auth-library`, with requested scope `https://www.googleapis.com/auth/maps-platform.places.textsearch` (listed in the Text Search contract). Production uses the attached `places-runtime@mom-im-ok-places.iam.gserviceaccount.com` identity and short-lived tokens. Headers are `Authorization: Bearer ...`, `X-Goog-User-Project`, `X-Goog-FieldMask` and `Content-Type`. The library refreshes tokens; no long-lived token is persisted by this provider. Tokens are never put in URLs or logs. No API key, new Secret Manager secret, service-account JSON key, GitHub secret/variable or owner credential import is required.

Owner preparation after review: update the Cloud Shell checkout, run the metadata-only migration plan, review `placesApiConsumerAction`, then owner-run apply to enable `places.googleapis.com` and create/reuse `projects/mom-im-ok-places/roles/placesApiConsumer`. Its only permission is `serviceusage.services.use`, bound to the runtime account on that quota project. See [quota project permissions](https://cloud.google.com/docs/quotas/set-quota-project). The role definition and unconditional runtime binding are validated fail-closed; extra/deleted permissions or unexpected runtime grants require review. Existing datastore access, deploy/build/App Engine IAM, WIF and runtime secret grants are preserved. CI gets no service-enablement permission. Review billing/Places quotas before manually deploying the reviewed commit. The development task does not perform any of these live steps.

## Fallback, provenance and Telegram

No usable Google match, unsupported feature, locality mismatch or ambiguity may try Nominatim. A resolved OSM candidate is accepted; Google ambiguity is preserved if OSM cannot resolve it, rather than choosing an arbitrary first Google result or pretending the city is unknown. Missing locality, insufficient evidence and explicit-city conflicts retain existing fail-closed states.

Only classified request timeout/abort, HTTP 429 and HTTP 5xx allow exception fallback, with fixed `google_places_fallback_used` diagnostic. ADC/config failures, HTTP 401/403, other request errors, malformed/oversized bodies and programming/contract errors fail closed through fixed `google_places_*` diagnostics. Upstream error bodies are never read/logged. Nominatim retains its own global rate gate, cache, User-Agent and OSM attribution; busy/rate/provider failures use the existing webhook retry path.

Google identity is `provider: google-places, id: <Place ID>`. Canonical IDs hash that identity, so repeated submissions dedupe transactionally while distinct Google branches remain distinct. References and supplied third-party attributions survive confirmation. Google proposals are plain Russian messages with a Google Maps link/attribution, rather than Telegram's map venue rendering. OSM proposals keep the venue rendering and OSM attribution. Provider names and geographic data are not translated UI strings.

Google-derived content is not OSM/ODbL data. Review [Google Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) for attribution, retention and external projection/export restrictions: the Place ID is exempt from caching restrictions; other Google content is not generally available for unrestricted permanent storage/reuse. This change preserves the requested canonical confirmation flow and provider provenance, without claiming that future exports or indefinite retention of all Google fields are licensed. There is no new shared cache of Google responses.

## Operational telemetry

Runtime logs JSON events with fixed fields only. `place_pipeline_stage` contains `stage`, bounded integer `durationMs` and `status`: stages are image_download, vision, web_verification, google_places and nominatim. Status values are ok, error, resolved, no_match, ambiguous, unresolved or city_unknown. `place_resolution` contains provider (google-places/nominatim/none), result (resolved/unresolved/city_unknown/failed) and the composed POI resolution duration. Download/inference/search stages are separately measured, including city correction/retry search. No venue/city/address/coordinates, images, raw updates, responses, credentials or user identifiers are logged. Error diagnostics remain English fixed codes; Telegram UI is Russian.
