# Google Places primary resolver

The production composition is `GooglePlacesPoi → FallbackPoi → NominatimPoi`. OpenAI vision/web verification supply bounded text only. Coordinates come from deterministic providers and require explicit Telegram confirmation. Google display/location content remains transient; the confirmed durable record retains only Google identity and evidence references.

## Protocol and matching

Use [Places API (New) Text Search](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places/searchText): `POST https://places.googleapis.com/v1/places:searchText`. There are at most three deduplicated query variants per resolution, ten results per response maximum and a ten-second deadline per query, no redirects and a 200 KB response bound. Only structured venue/native names, canonical/corrected locality, address clue and country are queried; images, visible text, Telegram captions/conversation/IDs are excluded. English is preferred; native names and cited aliases remain useful.

The field mask requests only `places.id`, `places.displayName`, `places.formattedAddress`, `places.location`, `places.types`, `places.addressComponents`, `places.attributions` and `nextPageToken`. Display name and geographic validation require Text Search Pro fields; no reviews, photos, opening hours, ratings or contact details are requested. A later ID-based refresh uses a separate bounded Place Details read, described below. There is no wildcard, pagination/research loop or Google response cache.

Names use bounded deterministic scoring, never Google ranking alone: normalized exact match 0.96, token-multiset equality/reordering 0.94, one-edit typo in Latin tokens of 7–64 characters 0.86, and distinctive partial signage 0.72. Generic restaurant/cafe/hotel/store/university words alone do not authorize a match. Partial matching needs a distinctive token of at least seven characters and at most one additional distinctive token; unrelated words are rejected. Multiple short distinctive tokens can identify a full name such as Sun Yat-Sen University. Scores are capped at 1 and receive locality +0.08, known matching country +0.04, compatible category +0.05 (unknown category +0.01) and matching address +0.06. A result requires score >=0.88 and margin >=0.12 over the runner-up. Similar branches remain ambiguous; lower-than-threshold competing candidates still participate in the margin. This deterministic confidence is an application heuristic, not a calibrated probability.

Wrong country/locality, incompatible known category, invalid identity/location or explicit conflicting house number reject. Address is normally a positive signal rather than a requirement: absence of a clue never blocks a strong match. Explicit numbered-street mismatch also rejects instead of trusting a different branch. House-number prefixes `No.`, `No` and `№` normalize away; Rd/Road, St/Street, Ave/Avenue, Blvd/Boulevard and Ln/Lane stay equivalent. 158 never becomes 1580/159. There is no unrestricted edit distance, fuzzy address search or guessed coordinate offset.

Queries use bounded native/canonical names, aliases or reordered terms and a distinctive partial/alternative visual clue, plus canonical locality/address/country. They use structured evidence only, never visibleText/images/raw conversation. One strong result stops further requests; otherwise candidates are combined by provider ID across at most three queries, with at most thirty result rows. Conflicting coordinates for the same ID fail closed. Multiple visual/verified identities in one locality can compete; conflicting localities still require clarification. A page token with plausible results preserves ambiguity because unseen competitors cannot be excluded.

City override is semantic intent, not a byte-exact name. OpenAI verification may emit a separate bounded `localityIntent` (canonicalName, aliases, countryCode, confidence) even when it finds no venue citation. The client binds it to the exact accepted city reply; confidence below 0.9 or a stale binding is ignored. This permits spelling/case/transliteration normalization without a Shanghai table. It supplies no coordinates/ID and is never persisted as Google content. Verified venue evidence in another canonical city/country still produces locality_conflict; Google locality/country must agree with intent aliases. Workspace hints remain weak. Model linguistic normalization is uncertain and must be judged against provider evidence.

Exactly one sufficiently separated ID is resolved. Similar scored candidates or a truncated matching page remain ambiguous. A contradictory duplicate ID/coordinate response is invalid. Google's [Place location / LatLng contract](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places#LatLng) specifies WGS84 unless otherwise stated; this implementation uses those coordinates directly without China-specific offsets or undocumented conversions.

## ADC, quota and owner preparation

Authentication uses [Application Default Credentials](https://cloud.google.com/docs/authentication/application-default-credentials) through `google-auth-library`, with the two operation-specific scopes `https://www.googleapis.com/auth/maps-platform.places.textsearch` and `https://www.googleapis.com/auth/maps-platform.places.details` (listed in the official Text Search and [Place Details contracts](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places/get)). Production uses the attached `places-runtime@mom-im-ok-places.iam.gserviceaccount.com` identity and short-lived tokens. Headers are `Authorization: Bearer ...`, `X-Goog-User-Project`, `X-Goog-FieldMask` and `Content-Type`. The library refreshes tokens; no long-lived token is persisted by this provider. Tokens are never put in URLs or logs. No API key, new Secret Manager secret, service-account JSON key, GitHub secret/variable or owner credential import is required.

Owner preparation after review: update the Cloud Shell checkout, run the metadata-only migration plan, review `placesApiConsumerAction`, then owner-run apply to enable `places.googleapis.com` and create/reuse `projects/mom-im-ok-places/roles/placesApiConsumer`. Its only permission is `serviceusage.services.use`, bound to the runtime account on that quota project. See [quota project permissions](https://cloud.google.com/docs/quotas/set-quota-project). The role definition and unconditional runtime binding are validated fail-closed; extra/deleted permissions or unexpected runtime grants require review. Existing datastore access, deploy/build/App Engine IAM, WIF and runtime secret grants are preserved. CI gets no service-enablement permission. Review billing/Places quotas before manually deploying the reviewed commit. The development task does not perform any of these live steps.

## Fallback, provenance and Telegram

No usable Google match, unsupported feature, locality mismatch or ambiguity may try Nominatim. A resolved OSM candidate is accepted; Google ambiguity is preserved if OSM cannot resolve it, rather than choosing an arbitrary first Google result or pretending the city is unknown. Missing locality, insufficient evidence and explicit-city conflicts retain existing fail-closed states.

Only classified request timeout/abort, HTTP 429 and HTTP 5xx allow exception fallback, with fixed `google_places_fallback_used` diagnostic. ADC/config failures, HTTP 401/403, other request errors, malformed/oversized bodies and programming/contract errors fail closed through fixed `google_places_*` diagnostics. Upstream error bodies are never read/logged. Nominatim retains its own global rate gate, cache, User-Agent and OSM attribution; busy/rate/provider failures use the existing webhook retry path.

## Durable identity versus transient display

Google identity is `provider: google-places, id: <Place ID>`. Canonical IDs continue to hash that identity, so repeated submissions dedupe transactionally while distinct branches remain distinct. A Google `Place` stores only id/workspaceId, providerIdentity, source/evidence references, confirmed/archived status, user tags and timestamps. It has no canonicalName/nativeName/aliases/category/confidence, formatted address, coordinates, Google types or attribution metadata. Independent vision Recognition remains in Discovery, explicitly separate from provider authority; web-verification citation references remain evidence. The provider's displayName is never silently relabeled as independently sourced.

The strict durable schemas also prevent Google content from being retained in pending, cancelled or confirmed Discovery candidates: `StoredCandidate` holds the Google identity, deterministic resolution marker and references only. The service passes a separate in-memory `DiscoveryView.liveCandidate` directly to Telegram for the initial proposal; this field is not part of the Firestore Discovery schema. Retrying a proposal after reloading its Discovery refreshes the live display by ID without rerunning vision/web search. No Google content cache, TTL cleanup dependency or persisted display snapshot is introduced. Raw live Google candidates and enriched Google Places are rejected on every repository write path.

Telegram proposals continue to show live name/address, a Google Maps link and required Google/supplied third-party attribution. Google content is displayed as a plain Russian message rather than on Telegram's non-Google venue map. That message remains with Telegram; this separation prevents it becoming our reusable Firestore dataset and does not claim deletion/control of already-delivered external messages. OSM proposals retain venue rendering and OSM attribution.

`GooglePlacesPoi.refresh(providerIdentity)` (also available through `FallbackPoi`/the optional `PoiProvider.refresh` port) returns a transient `PlaceDisplay`, never a canonical `Place`. It makes one authenticated `GET https://places.googleapis.com/v1/places/<Place ID>` with field mask `id,displayName,formattedAddress,location,attributions`, a ten-second deadline and 200 KB response bound. IDs and returned identity are checked, including missing/invalid location/display fields. It uses the same ADC/quota headers, fixed safe error codes and no upstream-error-body logging as Text Search. Refresh errors remain errors; a stored Google identity cannot silently become an OSM point. Present attributions must accompany any later display.

Future projection/export adapters must request a fresh provider view by the stored Google ID and independently respect [Google Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) for the destination, attribution and retention. Refresh availability does not grant unrestricted caching or external redistribution. No external export adapter is implemented here. For Google records, absence of canonical coordinates is intentional; the Place ID is the durable anchor exempt from the provider-content caching restriction. Nominatim Places retain their previous canonical name/address/WGS84 coordinates/category/evidence/attribution handling under OSM/ODbL.

This fix precedes production deployment of the Google resolver. It does not migrate or scrub live cloud data, deploy, change the webhook or make live Places calls. If Google content from an earlier version exists elsewhere, it requires separate owner-reviewed cleanup; these schemas reject the old Google-enriched records rather than trust their fields.

## Operational telemetry

Runtime logs JSON events with fixed fields only. `place_pipeline_stage` contains `stage`, bounded integer `durationMs` and `status`: stages are image_download, vision, web_verification, google_places and nominatim. Status values are ok, error, resolved, no_match, ambiguous, unresolved or city_unknown. `place_resolution` contains provider (google-places/nominatim/none), result (resolved/unresolved/city_unknown/failed) and the composed POI resolution duration. Download/inference/search stages are separately measured, including city correction/retry search. No venue/city/address/coordinates, images, raw updates, responses, credentials or user identifiers are logged. Error diagnostics remain English fixed codes; Telegram UI is Russian.

`google_places_filter` is emitted once per actual Text Search query. It contains only query number (1–3), bounded integer counts (0–10): returned, complete, nameStrong, categoryCompatible, localityCompatible, addressCompatible, accepted; result enum resolved/ambiguous/no_match; and fixed rejection counts no_name_match, category_conflict, country_conflict, locality_conflict, address_conflict, below_threshold, ambiguous_score. No names, text, addresses, coordinates, IDs, scores, tokens or upstream bodies are included. Diagnostics are best effort and do not change resolution.
