# Telegram privacy and confirmation

The private group is the trust boundary. One configured `TELEGRAM_CHAT_ID` is required; group/supergroup context, a sender and `is_bot:false` are required. Any human participant can use the bot. There is no configured per-user restriction. Other chats and unsupported commands are ignored. Normal conversation and captions are never application input, persisted, sent to AI or logged.

Register only `message` and `callback_query`. POST and JSON content type are checked first, then the secret header with constant-time comparison, then the bounded raw body, narrow structure, configured chat and human sender. Firebase's HTTP framework may parse before user code; application code ignores `req.body`. Inline-message callbacks and inaccessible/malformed callback messages are rejected. Authorized message-backed unknown callback data is acknowledged safely, with no discovery mutation. The callback is answered before expensive work, including duplicate deliveries, so the spinner does not wait for verification.

Send a photo, album or JPEG/PNG/WebP image document. Captions are ignored. Downloads enforce ten images, 5 MiB/image and 25 MiB/batch. Vision produces reusable Recognition; Google searches first, and optional SIWC web enrichment reformulates unresolved evidence before a second Google phase. Deterministic providers alone supply identity/coordinates. OSM proposals use `sendVenue` when address/coordinates are usable. Google proposals use a plain message with Google Maps link/attribution, without rendering Google content on another map. It includes **✅ Добавить / ✏️ Изменить город / ❌ Отмена** for resolved candidates. Unresolved proposals expose Изменить город / Отмена and never offer confirmation.

Confirm creates/reuses one canonical Firestore Place, or all explicitly selected Places atomically, and marks Discovery confirmed in one transaction. This is the milestone's “map update”; no external map projection is implemented. Cancel marks Discovery cancelled without creating a Place. Buttons are removed and a concise completion message is sent. Repeats are ignored or return already handled. A confirm/cancel race has one terminal winner. A stale proposal cannot alter a newer revision.

Change city invalidates the old proposal, removes its buttons, and sends a selective ForceReply asking for city/region. The ten-minute record contains workspace scope, discovery/version, requesting Telegram user ID, prompt message ID, expiry and processing status. That user ID owns one interaction; it is not configured authorization. A direct reply to that exact active prompt by the same human can proceed. When there is exactly one active city prompt owned by that human, their next nonempty ordinary text message of at most 200 characters also becomes its city reply; otherwise ordinary text is ignored. City is normalized, nonempty, at most 200 characters and has no control characters. Wrong-user/wrong-prompt/expired replies and ordinary text outside a unique active owned session are ignored without creating ingress records. Only normalized accepted city is stored; raw Telegram updates are never stored. Correction reuses Recognition and reruns bounded Google-first resolution with optional enrichment; it does not change workspace `/area`. The old proposal is superseded and a new proposal gets a new revision/token.

Only provider ambiguity that city would materially disambiguate asks for city through this narrow prompt. Known-locality POI absence, unsupported feature categories, insufficient evidence or explicit correction conflicts produce an unresolved message with Change city / Cancel, without an automatic prompt. Transient provider timeouts/429/appropriate 5xx keep the existing fallback/webhook retry path; they do not become city questions. Initial prompt ownership belongs to the image sender; another human may choose Change city to take ownership of a new edit. If a corrected city conflicts with cited locality evidence or still cannot resolve the location, the bot explicitly reports this and offers a manual city edit or cancellation, without a prompt loop. Workspace `/area` never overrides a corrected or verified city. No usable clues produce a concise request for a better screenshot, no Place and no city prompt.

Callback data contains only a short opaque hash token and action code (36 bytes), never IDs, city/address, URLs or secrets. Durable `telegramInteractions` map tokens to discovery revisions, proposal/prompt messages, expiry and processing leases. `cityPrompts` map exact reply message IDs to records. Proposals expire after 24 hours; expired/stale callbacks do not alter Discovery/Place. Transport delivery IDs and leases deduplicate work across cold starts. Interaction documents are backend-only even if future Firebase members are attached.

Albums still arrive as individual Telegram updates. Firestore debounce waits 1.5 seconds of quiet, seals at most ten deduplicated file IDs and processes one normal album once. A global image lease bounds memory and city-resolution work. Duplicates of completed ingress return 200; busy/transiently failed work returns 503 for Telegram retry. Late members of sealed/full albums become separate single-image discoveries. Ingress leases fence expired owners and last 330 seconds, beyond the function timeout. All work is awaited before HTTP response; no scheduler, queue or background polling is introduced.

Firestore domain confirmation is transactional/idempotent. Telegram external sends cannot be exactly-once: a crash after send but before recording its returned message ID can leave a duplicate/orphan proposal or ForceReply on retry. Only the recorded active prompt/proposal can mutate the matching discovery revision, so an orphan remains harmless. External inference can repeat before Recognition is committed; after that point city edits/retries reuse it. Telegram retry retention is finite; resend affected images if it expires. Interaction/inbox records and expired cache rows are retained for idempotency; expiration is enforced on reads, without a TTL/scheduler cost.

`/help` explains this flow. `/area <city or region>` is an optional bounded workspace hint shared by future submissions; discovery city correction never overwrites it. `/find`, `/branches` and replaceable external map/export projections remain future work; no custom mobile/map app is planned. See [owner operations](../infra/README.md) and [geographic policy/limitations](geography.md).

All bot-authored Telegram messages are Russian, including /help, /area acknowledgements, callback acknowledgement, missing-place/unknown-city prompts and unresolved/confirmed/cancelled results. Provider venue/address text and attribution names retain their original language. Diagnostics remain fixed English codes.

For a valid image/document or debounced album, the claimed ingress sends `🔎 Ищу место…` before model validation/download/inference. A backend-only child record `pendingIngress/{id}/status/processing` stores only a send claim and returned message ID; retries never resend the acknowledgement. At successful completion it is deleted best-effort before the proposal or single ForceReply. Send/storage/delete errors do not fail or retry the place pipeline. A crash after sending but before recording its ID can leave an undeletable orphan; preserving the prior send claim avoids duplicate status messages at the cost of occasionally missing an acknowledgement after a crash. Recoverable processing failures can leave the status until a later successful retry. No TTL/job is introduced.

Initial provider city ambiguity without a correction sends only the owned ForceReply, without a separate “city unknown” proposal. Changed/corrected unresolved results retain manual edit/cancel behavior. City intent normalization can fix spelling, language or script in the existing bounded verification flow; no extra inference or coordinates are generated for normalization.

An accepted owned city ForceReply starts one `🔎 Уточняю место…` status before waiting for the global processing slot or running verification. The same durable logical-reply claim prevents duplicate status sends on retry; successful work removes it best-effort before the proposal. A typed deterministic Google parser/adapter failure marks Discovery failed (empty candidates and fixed reason), records that reason in completed Ingress and returns HTTP 200. Expensive verification is not immediately repeated for the same update. A later terminal proposal-refresh failure uses the same path. Terminal state cannot be confirmed or reopened by stale city/callback actions.

Terminal errors claim one notification and prefer editing the recorded processing message into `⚠️ Не удалось обработать место из-за ошибки сервиса. Попробуй ещё раз позже.` If editing is unavailable, deletion and one replacement message are best effort. No internal diagnostic code is shown. Status child records store only boolean send/error claims and message ID, never provider content. As with status sends, a crash around Telegram effects or API/storage failure can lose an acknowledgement or leave an orphan; claims favor avoiding duplicate spam and retries never restart terminal provider work. A new image is a new logical request; terminal failures do not disable future requests.

Active-city text fallback uses backend-only `citySessions/{chat_user}` pointers, not collection scans. Metadata records bounded prompt tokens/IDs, discovery/revision/expiry and a reserved logical reply ID; normalized city is retained only in the existing owned interaction/discovery after acceptance. At most sixteen pointer entries/owners are retained as a metadata safeguard; overflow is blocked for plain-text selection until expiry. Multiple active prompts require explicit Reply. The first eligible text reserves one reply ID atomically; another message cannot steal that session, and retries reuse the binding. Successful city consumption, terminal failure, cancellation/confirmation and superseding prompts deactivate matching pointers; expired/stale entries are pruned on access. Completed deliveries never re-run provider work. A prompt registered during a concurrent lookup is preserved but cannot be guessed from an older read.

ForceReply remains enabled. The accepted plain-text path uses the same chat/human validation, owned prompt/revision checks, Ingress idempotency, `🔎 Уточняю место…` acknowledgement and terminal-error handling as explicit replies. Wrong chats/bots/commands/empty/overlong text and replies to unrelated messages never enter this fallback. Normal conversation outside a unique active owned session is neither persisted nor sent to AI/providers.

Google proposals show a deterministic confidence tier (high/medium/low), the live place card, Google Maps link and attribution. Missing locality alone does not discard a unique meaningful candidate, even after an explicit city edit. Medium/low cards clearly say the result is uncertain and ask the user to inspect the map and confirm. Reliable geographic/address conflicts and comparable unresolved branches remain blocked. A proposal never saves a Place automatically.

The current Google shortlist is a single revision-fenced multi-select menu (up to eight candidates). Checkbox toggles retain all candidates. Select all/Clear only change selection; Add Selected atomically confirms all chosen identities. A single eligible result uses singular confirmation, including old pending one-item shortlists. See [Chain selection](chain-selection.md) for labels, licensing and compatibility.
