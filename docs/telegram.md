# Telegram privacy and confirmation

The private group is the trust boundary. One configured `TELEGRAM_CHAT_ID` is required; group/supergroup context, a sender and `is_bot:false` are required. Any human participant can use the bot. There is no configured per-user restriction. Other chats and unsupported commands are ignored. Normal conversation and captions are never application input, persisted, sent to AI or logged.

Register only `message` and `callback_query`. POST and JSON content type are checked first, then the secret header with constant-time comparison, then the bounded raw body, narrow structure, configured chat and human sender. Firebase's HTTP framework may parse before user code; application code ignores `req.body`. Inline-message callbacks and inaccessible/malformed callback messages are rejected. Authorized message-backed unknown callback data is acknowledged safely, with no discovery mutation. The callback is answered before expensive work, including duplicate deliveries, so the spinner does not wait for verification.

Send a photo, album or JPEG/PNG/WebP image document. Captions are ignored. Downloads enforce ten images, 5 MiB/image and 25 MiB/batch. Vision produces reusable Recognition; optional SIWC web search checks public textual evidence; deterministic POI lookup supplies coordinates. The proposal uses `sendVenue` when address/coordinates are usable, otherwise a clear message. It includes **✅ Confirm / ✏️ Change city / ❌ Cancel** for resolved candidates. Unresolved proposals expose Change city / Cancel and never offer confirmation.

Confirm creates/reuses one canonical Firestore Place and marks Discovery confirmed in one transaction. This is the milestone's “map update”; no external map projection is implemented. Cancel marks Discovery cancelled without creating a Place. Buttons are removed and a concise completion message is sent. Repeats are ignored or return already handled. A confirm/cancel race has one terminal winner. A stale proposal cannot alter a newer revision.

Change city invalidates the old proposal, removes its buttons, and sends a selective ForceReply asking for city/region. The ten-minute record contains workspace scope, discovery/version, requesting Telegram user ID, prompt message ID, expiry and processing status. That user ID owns one interaction; it is not configured authorization. Only a direct reply to that exact active prompt by that same human in the configured group can proceed. City is normalized, nonempty, at most 200 characters and has no control characters. Wrong-user/wrong-prompt/expired replies and unrelated ordinary text are ignored without creating ingress records. Only normalized accepted city is stored; raw Telegram updates are never stored. Correction reuses Recognition and reruns search/POI only; it does not change workspace `/area`. The old proposal is superseded and a new proposal gets a new revision/token.

Only genuinely missing/ambiguous locality asks for city through this narrow prompt. Known-locality POI absence, unsupported feature categories, multiple branches, insufficient evidence or explicit correction conflicts produce an unresolved message with Change city / Cancel, without an automatic prompt. Provider timeouts/failures keep the existing webhook retry path; they do not become city questions. Initial prompt ownership belongs to the image sender; another human may choose Change city to take ownership of a new edit. If a corrected city conflicts with cited locality evidence or still cannot resolve the location, the bot explicitly reports this and offers a manual city edit or cancellation, without a prompt loop. Workspace `/area` never overrides a corrected or verified city. No usable clues produce a concise request for a better screenshot, no Place and no city prompt.

Callback data contains only a short opaque hash token and action code (36 bytes), never IDs, city/address, URLs or secrets. Durable `telegramInteractions` map tokens to discovery revisions, proposal/prompt messages, expiry and processing leases. `cityPrompts` map exact reply message IDs to records. Proposals expire after 24 hours; expired/stale callbacks do not alter Discovery/Place. Transport delivery IDs and leases deduplicate work across cold starts. Interaction documents are backend-only even if future Firebase members are attached.

Albums still arrive as individual Telegram updates. Firestore debounce waits 1.5 seconds of quiet, seals at most ten deduplicated file IDs and processes one normal album once. A global image lease bounds memory and city-resolution work. Duplicates of completed ingress return 200; busy/failed work returns 503 for Telegram retry. Late members of sealed/full albums become separate single-image discoveries. Ingress leases fence expired owners and last 330 seconds, beyond the function timeout. All work is awaited before HTTP response; no scheduler, queue or background polling is introduced.

Firestore domain confirmation is transactional/idempotent. Telegram external sends cannot be exactly-once: a crash after send but before recording its returned message ID can leave a duplicate/orphan proposal or ForceReply on retry. Only the recorded active prompt/proposal can mutate the matching discovery revision, so an orphan remains harmless. External inference can repeat before Recognition is committed; after that point city edits/retries reuse it. Telegram retry retention is finite; resend affected images if it expires. Interaction/inbox records and expired cache rows are retained for idempotency; expiration is enforced on reads, without a TTL/scheduler cost.

`/help` explains this flow. `/area <city or region>` is an optional bounded workspace hint shared by future submissions; discovery city correction never overwrites it. `/find`, `/branches` and replaceable external map/export projections remain future work; no custom mobile/map app is planned.
