# Geographic verification and deterministic POI providers

[Google Places API (New)](google-places.md) is the primary deterministic source, authenticated with runtime ADC. Public Nominatim/OSM is the fallback; its existing cache, global gate and attribution remain in force. Neither provider accepts AI coordinates.

The developer selected public Nominatim as a fallback for this small, user-triggered private-group venue workflow. Before using it, read the [official public Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/), rechecked on 2026-10-05. It requires an identifiable User-Agent, an application-wide maximum of one request/second, caching and visible OpenStreetMap attribution. It prohibits bulk/systematic POI harvesting, autocomplete, confidential/personal data submissions and generic geocoding services generated by low-code platforms. This application is a bounded personal venue workflow, not a public search API. The owner is responsible for continued compliance; switch providers if usage grows or service access is withdrawn.

`OpenAiSearch` reuses the same OpenAiOAuth, Secret Manager SessionStore and refresh lease as vision. It sends at most three bounded name/category/vision-locality clues, a separate explicit cityOverride and a weak workspaceAreaHint as JSON data, never images, visibleText, captions or conversation. Static instructions treat clues, city hints and web pages as untrusted. Requests use `store:false`, `stream:true`, `web_search` with low context, a 45-second timeout and bounded streamed output. SIWC forbids `max_output_tokens` and `max_tool_calls`; they are omitted. The client cancels/rejects a stream on a third search item and accepts at most three textual candidates and twenty protocol citations. There is one 45-second inference request, with up to two admitted web-search operations (one initial formulation and one reformulation), no open-ended research loop. SIWC has no supported max_tool_calls parameter; the prompt requests two and the stream reader fails closed/cancels on a third. This admission bound does not guarantee that a hosted third tool call has not started upstream before its event arrives. Hosted search availability depends on selected model and account/workspace policy; its internal work cannot be guaranteed to have a strict billing-token limit.

Only `url_citation` annotations in Responses events/completed output, coupled with a completed web search, become references. Model JSON cannot supply URLs or coordinates. No model-provided URL is fetched. HTTP 400 tool/options rejection returns unavailable textual verification; a single high-confidence vision clue with a vision locality or explicit correction may still go to deterministic lookup. Workspace hint alone cannot identify a branch; it may inform verification but does not authorize POI selection. Auth/permission failures, malformed output and other failures remain visible and fail closed; Gemini is never a search fallback. The owner reports successful live vision/web verification; new Google provider behavior is validated with credential-free fixtures, not live requests.

`PoiProvider` is replaceable. `NominatimPoi` makes at most one `/search` request per resolution, jsonv2, limit three, a project-identifying User-Agent, no redirects, a ten-second timeout and a 100 KB response limit. It uses a seven-day Firestore cache keyed by endpoint and normalized query hash, including negative results. A transactional global gate permits only one in-flight request across instances/revisions, at least 1.5 seconds between completed requests, and at most fifty new requests/day. Busy requests fail for webhook retry instead of launching a parallel burst. A crashed gate owner expires after thirty seconds, beyond the request timeout. Rate state is outside the workspace so workspaces cannot multiply endpoint traffic. These small caps are ceilings, not a target request rate.

Queries contain only public venue/local name, canonical locality and public address clues. Private conversation, full visible text, image bytes, URLs, credentials and Telegram identities are excluded. Do not enter confidential material into `/area` or a city reply.

Context is explicit: a user cityOverride is a hard constraint; conflicting cited verification returns locality_conflict without querying another city. Verification carries a separate bounded, high-confidence localityIntent for the exact city reply. Linguistic spelling/transliteration normalization needs no web citation; venue claims still require actual web-search citations. Provider locality/country must agree with the semantic intent, and contradictory verified venue evidence still fails closed. Verified city wins over a vision area clue. Both win over workspaceAreaHint, which is only weak search context; a hint alone never authorizes choosing a same-name branch. Multiple verified localities require city clarification; a correction can narrow them only to matching verified locality aliases.

[Official Nominatim search documentation](https://nominatim.org/release-docs/latest/api/Search/#language-of-results) notes that clients without Accept-Language often receive local names. We send `Accept-Language: en` and `accept-language=en`, prefer the cited canonical city, retain native venue names/namedetails and match bounded verified cityAliases against returned locality fields. NFKC/case/space normalization and removal of a terminal 市 from entirely Han-script city names equate 上海/上海市 without transliterating arbitrary strings or conflating unrelated administrative areas. Optional uppercase ISO countryCode becomes `countrycodes` and is rechecked against result country_code. Language/country are included in cache identity, avoiding reuse of older unspecified-language output.

Branch protection prefers city/municipality, falling back to town/village only when higher-level locality is absent. A same-name lower-level town cannot mask another city. China's province-level municipality can appear as state: only when city/town fields are absent does a matching CN-BJ/CN-SH/CN-TJ/CN-CQ address ISO code admit that state field. A rural county is considered only when no named city/town/municipality exists; a broad county/state/country cannot mask a conflicting city. Missing aliases, traditional-character variants without cited aliases, untranslated locality ambiguity and sparse OSM coverage still fail closed. English is a preference, not a promise of translated upstream names.

Strong normalized venue name/alias matching, valid WGS84 coordinates, OSM type/id and matching locality/country are always required. Existing amenity/shop/tourism/leisure/historic support remains, including restaurants, cafes and viewpoints. Additional categories are explicit key/value pairs: natural peaks/volcanoes/hills/cliffs/cave entrances/beaches/bays/capes/springs/water/woods/glaciers/rocks/arches/stones; place islands/islets/squares; man_made lighthouses/towers/observatories/windmills; waterway waterfalls; geological palaeontological sites/outcrops. Generic settlement/address/building/highway/infrastructure results are excluded. Only one matching deterministic POI becomes selectable and always requires human confirmation; multiple branches remain ambiguous.

The provider returns resolved, city_unknown (missing/ambiguous locality), or unresolved (no match, unsupported category, ambiguous POI, insufficient evidence or locality conflict/mismatch). The core persists a reason, and only genuinely missing/ambiguous locality automatically asks for city. If city is known but the venue remains absent from both providers or ambiguous, the UI states the resolution failure and offers Change city / Cancel. Corrected-city failures do not loop into automatic prompts. Temporary provider failures throw fixed diagnostics for webhook retry, not city clarification. Primary coverage depends on Google Places; fallback coverage depends on actual OSM data. No coordinates are invented.

Set optional non-secret `NOMINATIM_ENDPOINT` in the GitHub production environment to a compatible HTTPS origin when changing services; no source update is required. Default is the public endpoint. Changing it creates a separate cache key, while the conservative global gate remains. The runtime displays `© Участники OpenStreetMap (ODbL)` on proposals and retains OSM references in canonical Places. Observe [ODbL obligations](https://www.openstreetmap.org/copyright) when later exporting/sharing substantial datasets.

Place IDs hash stable provider identity (Google Place ID or OSM type/id), scoped by the workspace collection. Without a stable identity, the fallback hashes normalized name plus coordinates rounded to six decimals; it intentionally avoids fuzzy chain-name merging. Distinct branches with distinct IDs/positions remain distinct. Confirm reads Discovery and Place before writes in one Firestore transaction, creates the Place only if absent, and updates terminal status/link together. Cancel creates no Place. Compare-and-set discovery revisions invalidate old proposals after a city edit and serialize confirmation versus cancellation.

Google confirmation stores identity and evidence references only, including in Discovery candidates. Google names, addresses, coordinates, types and attributions remain transient in-memory display data; refreshing a stored Google Place ID performs a bounded authenticated Place Details read, with no substitution of OSM identity on refresh failure. Nominatim canonical persistence and its cache remain unchanged. See [the persistence boundary](google-places.md#durable-identity-versus-transient-display) before building future exports.

Google resolution now separates search eligibility from acceptance: every schema-valid clue may search without a city/confidence gate. Production first runs at most two Google queries; a strong unique result skips web verification. Otherwise one enrichment invocation (existing maximum two web_search operations) precedes at most two more Google queries. Explicit city intent and provider conflicts remain strict, as do deterministic identity/coordinates, explicit name evidence and branch competition. Numeric ranks are not absolute acceptance gates. Unknown-city cross-city branch ambiguity asks for city; mere absence of an AI locality does not. Nominatim's conservative selectLocality, rate gate and cache are unchanged. See [Google control flow](google-places.md#search-eligibility-and-resolution-control-flow).
